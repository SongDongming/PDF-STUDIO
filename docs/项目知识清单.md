# PDF-Studio 项目知识清单

> 目标读者：刚接手这个项目、想真正看懂它的人。
> 这一份讲清楚：**它是什么 · 为什么这么选型 · 数据怎么流动 · 每个模块干什么 · 从哪里开始读**。

---

## 1. 一句话定位

**PDF-Studio 是一个"把 PDF 变成可对话的知识库"的系统**：
上传 PDF → 机器把每页拆成文字/图表/表格/公式 → 建向量索引 → 抽知识图谱 → 自动编 Wiki → 你提问，它带着**可点击的原文证据**回答你，还能打开 PDF 原页看到命中的位置。

它不是简单的"PDF 全文搜索"，而是**多模态 + 可溯源（grounded）**的检索引擎。

> 打个比方：别人给的是一堆 PDF 文件；PDF-Studio 给你的是**一座会自己整理的书架 + 一个会翻书找答案、并在每一页画重点给你看的助手**。

## 2. 技术栈全景（为什么选这些）

| 层 | 技术 | 干什么 | 为什么选它 |
|---|---|---|---|
| 前端框架 | **React 19 + Vite + TypeScript** | 页面 UI | 生态大、组件化清晰；Vite 开发热更新快 |
| 前端图表 | **AntV G6 5.x** | 知识图谱可视化 | 图渲染能力成熟，支持缩放/拖拽/布局 |
| 后端框架 | **FastAPI** | REST + SSE 接口 | 异步性能好、自带 Swagger 文档、类型友好 |
| 数据持久化 | **PostgreSQL + SQLAlchemy** | 业务状态快照 | 稳定、成熟；存"应用状态快照"而非传统业务表 |
| 对象存储 | **MinIO** | PDF 源文件 / 编译产物 / 素材图 | S3 兼容、轻量，Docker 一键起 |
| 知识图谱 | **Neo4j + APOC** | 实体/主张/关系图 | 图数据库，多跳关系查询天然高效 |
| LLM | **DeepSeek V4 Flash** | 问答 / 图谱抽取 / 富化 | 便宜、中文强、走 OpenAI 兼容协议好接 |
| Embedding | **智谱 GLM embedding-3**（1024 维） | 把文本转成向量 | 中文向量效果好，免费额度够用 |
| OCR | **PaddleOCR-VL-1.6**（飞桨官方 API） | 版面解析（文字/图/表/公式 + 坐标） | 中文版面识别强，走官方 API 不用本地跑模型 |
| 任务执行 | **进程内 LocalJobRunner**（无 Celery/Redis） | 后台编译/重建任务 | 单进程足够、无额外组件、状态好保证一致 |
| 容器化 | **Docker Compose**（单端口 nginx） | 一键部署 | 全容器化，服务器上一条命令跑起来 |

**一句话总结选型思路**：能少一个组件就少一个（砍掉 Celery/Redis/alembic），优先用 OpenAI 兼容协议把各家模型统一接进来，用"快照持久化 + 进程内任务"换架构简单。

## 4. 核心业务流程

### 4.1 上传 → 编译（文档入库）

这是最核心的一条链，把一份 PDF 变成"可检索 + 可进图谱 + 可编 Wiki"的知识单元：

```
上传 PDF
  → 存进 MinIO（source 对象）
  → 创建编译任务（LocalJobRunner 后台跑）
     1. 渲染每页 → PyMuPDF 生成页面图
     2. OCR 每页 → ocr_bridge → 飞桨 PaddleOCR-VL
        （拿到文字/图片/表格/公式 + 每块的精确坐标 bbox）
     3. 归一化元素 + 物化素材（裁出图表存 MinIO）
     4. 生成结构化 Markdown
     5. 切分成可检索的 chunk（片段，带页码/坐标/素材引用）
     6. 写不可变的编译清单（manifest）
     7. 富化（可选）：LLM 给图表写语义描述 → 语义产物
     8. 建混合检索索引（chunk 文字 + 向量）
     9. 图谱抽取：LLM 从内容抽 实体/主张/关系 → 提交 Neo4j
    10. Wiki 重建：从更新后的图谱重新编译 Wiki 页面
```

涉及的关键文件：
- 路由入口：`backend/app/api/routes/documents.py`（upload / compile / reindex）
- 编译核心：`backend/app/store.py::compile_document_now`
- 实际编译：`backend/app/services/ingestion.py::DocumentCompiler`
- OCR：`backend/app/services/ocr_client.py` + `operations/local/ocr_bridge.py`
- 索引：`backend/app/services/indexing.py`
- 富化：`backend/app/services/enrichment.py`

### 4.2 问答（Agentic RAG）

```
你提问
  → 规划器（DeepSeek）判断：这问题要不要查知识库？
     不需要 → 直接通用知识回答（明确标注无引用）
     需要   → 混合检索
        BM25 词法匹配 + 向量语义匹配 → RRF 融合 → 取 top chunk
  → DeepSeek 生成回答，且【只允许引用检索到的证据】
  → 校验：引用的 citation 必须真实存在、素材必须真实存在
     不通过 → 自修复重试
  → 前端渲染：回答 + 证据抽屉 + 点证据可打开 PDF 原页看到命中区域
```

关键特性：**可溯源（grounded）**。模型不能自己编页码/素材，每条引用都能点回 PDF 原页定位。这就是为什么叫"不是黑盒问答"。

涉及文件：
- 路由：`backend/app/api/routes/chat.py`（含 SSE 流式）
- 规划/回答：`backend/app/services/agent_runtime.py`（legacy 模式）
- 检索：`backend/app/services/retrieval.py`（BM25 + dense + RRF）
- 模型适配：`backend/app/services/providers.py`（DeepSeek，含 JSON 自修复）
- 前端：`src/App.tsx`（会话/流式）→ `src/components/ChatPanel.tsx` → `src/components/PdfViewer.tsx`（双栏对照）

### 4.3 知识图谱 & LLM Wiki

- **图谱**：编译后，LLM 从 chunk 里抽实体（如"PaddleOCR"）、主张（"PaddleOCR 支持版面识别"）、关系（"使用/包含/支持"），带证据连接，存进 Neo4j。回答时的证据能回溯到原始页面坐标。
- **Wiki**：从图谱的实体 + 关系自动编译成"技术百科"页面（每页有来源引用）。文档删了，图谱删了，Wiki 孤儿页自动消失。

涉及文件：`graph_extraction.py`、`graph_repository.py`、`wiki_graph.py`、`wiki_repository.py`

### 4.4 级联删除 / 数据一致性

删除一份文档会**全链路清理**，保证图谱/Wiki/索引/产物永远一致：
```
删文档 → 删检索 chunk → 删 Neo4j 图谱贡献 → 删 MinIO 编译产物
      → 从更新后图谱重建 Wiki（孤儿页消失）→ 删记录
```
（`store.py::remove_document_cascade` / `remove_knowledge_base_cascade`）
如果历史脏数据残留，还有 `POST /knowledge-bases/{id}/reconcile` 对账清理接口。

## 5. 关键设计决策与取舍（面试/汇报能用上）

| 决策 | 理由 |
|---|---|
| **不用 Celery/Redis**，用进程内 LocalJobRunner | 单进程足够；省两个组件；状态在内存 + 快照落库，天然一致。任务有超时看门狗，挂起任务自动失败不堵队列 |
| **状态用"版本化快照"而非传统业务表** | 后端把所有状态（知识库/文档/任务/会话/Wiki）放内存，每次变更把整个快照 CAS 落 Postgres。简单、重启可恢复、无迁移负担 |
| **混合检索 BM25 + 向量 + RRF** | 中文技术文档没有词典分词也能好的词法召回 + 语义召回互补；RRF 无参融合稳定 |
| **DeepSeek 用 `json_object` + jsonschema 自修复** | DeepSeek 拒绝 `json_schema` 响应格式（400），改在 system prompt 里写死 JSON Schema + 解析后校验、失败喂回模型重试 |
| **OCR 走官方 API + 本地桥** | 不用本地跑 PaddleOCR 模型（省资源），桥把后端契约翻译成飞桨异步任务 API |
| **单端口 nginx 部署** | 前端和后端同源，浏览器只访问一个端口，完全绕开 CORS 配置 |
| **内存适配器供测试** | Neo4j/对象存储都有 InMemory 版，pytest 不依赖外部服务 |

## 8. 学习路径（从哪开始读，建议顺序）

**第一步：跑起来 + 看界面**（建立直观印象）
1. 读 `README.md`
2. 启动后上传一份 PDF，走一遍「编译 → 提问 → 点证据看原文 → 看图谱 → 看 Wiki」

**第二步：读懂前端主干**
3. `src/api/client.ts`（后端接口怎么调的）
4. `src/hooks/useWorkspaceApi.tsx`（全局状态怎么来、怎么轮询）
5. `src/App.tsx`（会话和问答流怎么组织）

**第三步：读懂后端主干**
6. `backend/app/main.py`（启动时干什么）
7. `backend/app/store.py`（状态模型 + 编译编排，这是核心）
8. 跟着一个编译任务走：`documents.py` 路由 → `compile_document_now` → `ingestion.py`

**第四步：逐个能力**
9. 检索 + 问答：`retrieval.py` → `providers.py` → `agent_runtime.py`
10. 图谱 + Wiki：`graph_extraction.py` → `graph_repository.py` → `wiki_graph.py`
11. 部署：`infra/compose.yaml` + `infra/DEPLOY.md`

**阅读建议**：别从头到尾读文件，而是**跟着数据流走**——"上传一个 PDF 会发生什么"、"问一个问题会发生什么"，顺着调用链读，比按目录读高效得多。

## 9. 常见术语速查

| 术语 | 含义 |
|---|---|
| chunk | 把文档切成的小片段，检索的最小单位 |
| bbox | 元素在页面上的坐标框，用于"回到原文定位" |
| manifest | 一次编译的不可变结果清单（哪些页/元素/素材/chunk） |
| RRF | Reciprocal Rank Fusion，多路检索结果融合 |
| grounded / 证据溯源 | 回答必须基于真实检索到的内容，不能编造 |
| SSE | Server-Sent Events，后端把流式回答推给前端 |
| 富化 (enrichment) | LLM 给图表写语义描述，让图片也能被检索到 |
